# Plan builder on fuelsteps.com — design

Date: 2026-10-02 · Repo: `bruynr/fuelsteps-site` (branch `feature/plan-builder`) · Status: approved in chat, spec for review

## Goal

Garmin Connect only offers plain text fields for FuelSteps schedules (array settings don't save; Garmin bug since 2022). Typing the mini-syntax (`3x5 Gel 25 caf`) is the weak spot of the UX. Three things fix that, all on the website, none in the app:

1. **Settings format reference**: a precise, plainly worded description of the 10 settings fields per schedule and the step syntax, as normal HTML page text and in `llms-full.txt`, so that a human or an AI assistant (ChatGPT, Claude, Copilot, …) that reads the site can produce correct settings.
2. **Plan builder**: a page where a runner clicks a schedule together, sees the resulting moments and copies the generated field values into Garmin Connect.
3. **Usage analytics**: Umami (cookieless, no consent banner) for page views, referrers, countries and custom events in the builder. It replaces Cloudflare Web Analytics, which would only duplicate the page views.

Success: a user who asks their AI "give me a fuel plan with gel, gel caf and dextro, I use FuelSteps, what do I set?" gets 10 field values that paste without error; a user of the builder never types the syntax by hand; the Umami dashboard shows which templates, units and field copies are used.

Out of scope (v1): shareable URLs, a generator from distance + target g/h, editing the general settings (vibration, tone, alert offset), anything in the app itself beyond a link to the page.

- Own `<title>`, description, canonical, hreflang alternates (to `/plan/` in each language), Open Graph, `theme-color`, icons, `WebPage` JSON-LD. Same header/footer as the home page; the language switcher links to the plan page in the other language and remembers the choice (reuse `REMEMBER`). No browser-language redirect on the plan page (the user came from a localized link).
- Home page: a button "Build your schedule" in the hero and in the "Ready in a minute" step about editing schedules; `nav` link.
- `sitemap.xml` and the IndexNow URL list include all plan pages. `404.html` unchanged.
- Asset paths use the existing `up` convention; the plan page is one level deeper (`../` for English, `../../` for the other languages).

## 2. Settings format reference

Section on the plan page (below the builder, with an anchor `#format`) and verbatim in `llms-full.txt`; `llms.txt` gets a bullet "Settings format: see /plan/#format" and a short grammar line. The heading contains the words "FuelSteps settings format" (and the translation) so search and AI find it.

Content, source of truth = `ScheduleParser.mc` in the app repo:

- In Garmin Connect (Connect IQ app → My data fields → FuelSteps → Settings) each schedule has 10 fields: **Name** (max 16 characters), **Unit** (Distance = km, Time = min) and **Step 1 … Step 8** (text, max 40 characters). Unused step fields must contain `-` (Garmin Connect cannot save an empty text field). Fields are read in order; the first `-` or blank field ends the schedule.
- One step field = `[Nx] size [text] [carbs[g]] [caf]`, separated by spaces, in this order:
  - `Nx` repeat, optional, 1–30 (`3x5` = three times 5 km/min); the step is numbered `#1 … #N` on the watch.
  - `size` distance or time **after the previous moment**: km with unit Distance, minutes with unit Time; decimals with `.` or `,`; minimum 0.5 km / 5 min; the running total of the schedule may not exceed 100 km / 600 min.
  - `text` optional, may contain spaces (`Gel CAF`), default `Gel`. Everything between size and carbs/caf is text. A last word that is a number is read as carbs, so `5 Maurten 100` means 100 g.
  - `carbs` optional, whole grams, `25` or `25g`; default 0.
  - `caf` optional, any case, marks caffeine (counted in the activity, shown on the alert).
- `0` as size is allowed only in Step 1 and without repeat: the gel taken before the start; it counts in the totals but gives no alert.
- One invalid field makes the whole schedule invalid; the watch menu names the field number.
- Three examples (fields listed as Step 1 … Step 8) and one worked example: the question "gel, gel caf and dextro for a 32 km run" → Name `Long run`, Unit Distance, `0 Gel 25`, `10 Gel 25`, `3x5 Gel 25`, `5 Gel CAF 25 caf`, `-`, `-`, `-`, `-`, plus the moments it produces.
- The remaining llms texts are brought up to date in the same change: schedule 1 default is "Gel 5 km" (3× 5 km, 25 g gel with caffeine), the alert path is Alerts → Add New → Connect IQ → FuelSteps → On, and nothing fires until a schedule is picked on the watch (same wording as `STORE.md` / `README.md` in the app repo).

## 3. Builder

Vanilla JavaScript in two files (no framework, no build step): `plan-core.js` with the pure logic (ES module, also imported by the Node tests) and `plan.js` with the DOM code, loaded only on the plan page; all UI strings come from `i18n` and are injected into the HTML by `build.py`, `plan.js` reads them from `data-` attributes or an inline JSON block, so the script itself is language-neutral.

Layout (two columns on desktop, stacked on mobile):

**Left, input**
- Name (text, max 16), Unit (segmented km / min).
- Template select: "Gel 5 km" (`3x5 Gel 25 caf`), "Marathon 7 km" (`0 Gel 25`, `7 Gel 25`, `7 Dextro 15`, `7 Gel CAF 25 caf`, `2x7 Gel 25`), "Every 30 min" (time, `6x30 Gel 25`). Picking a template replaces the current steps (confirm when steps exist).
- Step rows (max 8): repeat (number 1–30, default 1), size (number, step 0.5 or 5), text (free), carbs (number, g), caffeine (checkbox), move up/down, delete. "Add step" button, disabled at 8.
- Live validation per row with the same rules as the watch, messages from i18n: below minimum, total above maximum, 0 only in step 1 without repeat, field longer than 40 characters, name longer than 16; hint when the last word of the text is a number.

**Right, output**
- The 10 Garmin Connect fields as labelled rows (Name, Unit, Step 1 … Step 8), each with a copy button; unused steps show `-`. Copy uses `navigator.clipboard.writeText` with a "Copied" flash.
- "Copy all" copies the ten lines as `Label: value` text, for pasting into notes or an AI chat.
- Moments preview: table with planned moment (km 5 / min 30), label with `#n` numbering, grams, caffeine mark; footer with total grams, number of moments, number of caffeine moments; for time schedules also g/h (total g / total h). Before-start step shown as "before start".
- Short line under the output: where to paste (Connect IQ → My data fields → FuelSteps → Settings → Save), then pick the schedule on the watch.

**State**: the current schedule is kept in `localStorage` (`fuelsteps-plan`) so a reload keeps it; first visit loads the "Gel 5 km" template.

**Core logic** (pure functions, exported for tests): `parseStepText(raw)` mirroring the Monkey C function token for token (repeat/size/text/carbs/caf, `-1`/`-2` x handling, 1–4 digit whole numbers, one `.`/`,` decimal), `validate(schedule)` with the rules above, `formatStep(step)` producing the canonical field text (`3x5 Gel 25 caf`: repeat omitted when 1, carbs omitted when 0, text always written so the line stays readable), `moments(schedule)` producing the preview rows and totals. Round trip `parse(format(step))` equals the step.

## 4. Analytics

- Umami Cloud script tag on all pages, replacing the Cloudflare beacon in `ANALYTICS` in `build.py`; website id `458f80aa-006c-4354-9a7b-8bdda8850cbd` in a constant `UMAMI_ID`, script `https://cloud.umami.is/script.js` with `defer` and `data-website-id`.
- Events only on the plan page, via `umami.track(name, data)` guarded by `typeof umami !== "undefined"`:
  - `plan_template` `{id}`
  - `plan_copy` `{field: "name" | "unit" | "step1" … "step8", unit: "km" | "min", steps: n}`
  - `plan_copy_all` `{unit, steps}`
- No personal data, no schedule contents, no cookies; the privacy line in the footer stays valid ("no account, no cookies").

## 5. Testing and verification

- `plan.test.js` with `node --test`: all cases from `StepTextTest.mc` ported (valid and invalid step texts), validation rules, formatting round trip, moments for the three templates. Runs in `pages.yml` before `python build.py` (`node --test` step, Node 20+ on `ubuntu-latest`), so a failing parser blocks the deploy.
- `python build.py` locally, then manual check with `playwright-cli` on `/plan/` and `/nl/plan/`: template load, add/move/delete, validation message, copy button, preview totals, localStorage reload, Umami event in the network log.
- Content check: `llms-full.txt` contains the format section and no stale text (6× 30 min, old alert path).
- Follow-up in the app repo (separate change): README and STORE.md link to `https://fuelsteps.com/plan/`.
